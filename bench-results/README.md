**How to read this table** (all figures tok/s, higher is better):

1. **Two context families.** The 2026-09-01/02 rows ran at `524288 x 4`, everything from 2026-09-03 on at `262144 x 6` (owner decision of 2026-09-02 evening, no measurement window). A delta that crosses the two families also carries the context change.
2. **Warm-up methodology changed at W1 (2026-09-03).** Before W1 the first prefill after a boot still carried the JIT compile of the mhc/topk/indexer shapes; from W1 on one pass is always run and discarded. The same engine therefore reads prefill-30k 1908 on 09-02 and 2075 at W1: that step is method, not gain.
3. **Boot-to-boot variance is +/-5% on decode.** Three boots of the identical production recipe on 2026-09-04 gave structured 58.8 / 58.3 / 55.8 tok/s. Three-run decode medians move +/-3-5%, prefill medians +/-2-3%. Deltas inside those bands are noise.
4. **Single-pass rows.** Rows flagged `single-pass` rest on one `run_ab.sh` pass; the others average two passes. A single pass is a weaker measurement, not a different one.
5. **Harness prose and by-hand prose are not interchangeable.** "Prose (harness)" is the `run_ab.sh` prose phase, "Prose (by hand)" is a separate `bench_decode.py --prompt prose` run; the `code` phase is never part of `run_ab.sh`. Where both exist the by-hand set is the settled one - the harness prose figure is the noisier of the two.
6. **Speculative-decoding acceptance is only comparable from 2026-09-04 on**, when the harness started snapshotting the `/metrics` counters per phase. Earlier figures were read by hand from the rank-0 log, so acceptance is not a column of this table.
7. **c4 aggregate is bimodal at k >= 5.** Wave aggregates split into a slow and a fast mode (fast waves sit at 220-233 tok/s); this is a property of the draft length, not of the adaptive policy, and it makes the c4 aggregate of any k >= 5 row noisy.
8. **Estimators.** `decode tok/s = (completion_tokens - 1) / (t_end - t_first_token)` per stream, `prefill tok/s = prompt_tokens / TTFT`; c4 aggregate is `tokens_total / (max stream end - min stream first token)` per wave, not 4x the per-stream median. Cells are the mean of the per-pass medians (median over the listed files for the by-hand code/prose columns). Definitions: `docs/bench.md` § Metric definitions.

## What is in here

- **`<ts>-<pid>-<label>.json`** — one file per pass of `scripts/bench/run_ab.sh` (harness v2).
  `<ts>` is `YYYYMMDD-HHMMSS` of the start, `<pid>` the pid of the run, `<label>` the variant
  name passed on the command line. Each file holds every phase of the pass (decode structured
  ×1, prose ×1, structured c4, optionally decode @1400, prefill ~30k, prefill ~100k) with the
  per-run rows, the medians, the needle answers and the `sizing_correction` block of the prefill
  phases.
- **`<date>-<name>.md`** — the note for a measurement window: what was compared, the matrix of
  medians, the reading and the decision taken.
- Files named `<date>-<label>-code.json` come from the `code` decode phase, which is run by hand
  with `bench_decode.py --prompt code` and is not part of `run_ab.sh`.

Every node name and address in this directory is a placeholder — the numbers are real, the
site-specific identifiers are not. Legend: `<ALIAS_RANK0>`…`<ALIAS_RANK3>` are the ssh
alias/hostname of the node at that rank (rank 0 is the API node), `<MGMT_IP_RANK0>`…
`<MGMT_IP_RANK3>` their management addresses (endpoint URLs in the JSON files read
`http://<MGMT_IP_RANK0>:8000/v1`), `<USER>` the login used on the nodes, `<FABRIC_IP>` an
address on one of the four point-to-point fabric /24s and `<LINK_LOCAL_IP>` a link-local
(`169.254/16`) address the NIC assigned itself. All of them are per-cluster values, replaced
by your own when you rerun the benchmarks or the `ncclbench` microbench.

Compare passes with:

```bash
python3 scripts/bench/compare.py bench-results/<passA>.json bench-results/<passB>.json
```

## The two studies

**2026-09-01 — 3-way comparison (historical, translated 2026-09-04).** NVFP4 vs EXL3 4bpw vs upstream FP8,
same harness, same client, consecutive windows. This is the study that led to keeping the FP8
lane and dropping the other two, so the NVFP4 and EXL3 recipes no longer exist in this repo;
the notes mention env files, containers and images that have since been removed. Kept for the
numbers and the reasoning.

**2026-09-02 — MTP vs DFlash2 (English).** On the FP8 lane: MTP k=3 vs MTP k=5 vs the DFlash2
drafter at k=7, plus an `--async-scheduling` arm. The study first fixed the recipe at DFlash2
k=7; a fourth window the same afternoon measured the same drafter at `SPEC_TOKENS=3` and **that
is what production kept** (prose-first). The recipe the repo ships today: FP8 zai-org weights +
DFlash2 drafter, k=3, async off.
