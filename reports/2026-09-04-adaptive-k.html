Adaptive draft length: letting each request pick its own speculation depth

Speculative decoding drafts k tokens per step and keeps the ones the model accepts. A fixed k=5 made structured and parallel workloads up to 50% faster but slowed prose by 10–19%. A 400-line scheduler patch now chooses k per request from its own acceptance history. Five threshold sets were measured in one day; this is what they gave, which one went to production, and what it costs.

Decision — v1 promoted, 4 September 2026, 12:05.

Production moves from fixed k=3 to adaptive k ∈ {3, 5}, variant v1: optimistic start at 5, band 0.42 / 0.58, alpha 0.15, position-3 signal, per request. Structured decode +19%, sustained decode +10%, four parallel streams +40% (201 mean, 225 on the fast waves), code +4%, at a prose cost of 6% single stream and 15–20% on long-context essay decode at one size. The table below recommended the safer v2; the owner chose v1 for three reasons.

  • The usage mix decides. About 50% parallel sub-agents driven by a third main model, 30% agentic coding with this stack as the primary model, 20% prose. Four-stream throughput and code decode therefore dominate the weighted cost, and they are what the optimistic start buys: 201 against 144 at k=3 and 170–177 in the arms that start at 3.
  • The prose cost is imperceptible. 40.2 against 42.9 tok/s by hand — about 41 instead of about 43 tokens per second is not visible to a reader at this speed. The same −4..−6% appears in all ten passes of all five arms, so protecting prose removes no residual and costs the whole concurrency gain.
  • Batch-uniform rejected. v4 and v5 give the whole batch one draft length: with concurrent heterogeneous requests the slowest stream governs k for everyone. Per-request mode lets each request keep its own, which is what a mixed sub-agent load is.

Costs accepted and recorded in the commit: prose −6% single stream, long-context essay decode −15..−20% on one size (100k 35.1 and 200k 36.2 against 43.8 / 42.5 at k=3), full decode CUDA graphs lost on mixed-k steps, prefill unchanged. Rollback in one step: SPEC_TOKENS=3, SPEC_EXTRA_JSON="", drop --scheduler-cls, drop the /opt/tp4 mount and the VLLM_ADAPTIVE_K_* variables.

Why a fixed k could not be promoted

The night sweep of k=3/4/5/7 with per-workload acceptance counters explained the trade. Structured output accepts 0.90–0.95 of drafted tokens at any k, prose only 0.32–0.47 above k=3. At small batch the MoE cost grows with the number of distinct experts the verify tokens touch, so a 6-token verify step costs about 20–25% more than a 4-token one. Where acceptance is high the extra tokens pay for it many times over; on prose they do not.

How the patch works

Where the decision livesIn vLLM's scheduler, not in the drafter. The drafter always drafts 5 tokens; the scheduler sets, per request, how many of them the next step verifies. The scheduler runs in one process and broadcasts its output to the four tensor-parallel ranks, so the decision is consistent by construction.
How it is installedA subclass of vLLM's AsyncScheduler selected with --scheduler-cls, bind-mounted from the repo and versioned like every other change. No file of the container image is replaced, so it survives image upgrades. One rollback line in cluster.env.
The signalPer request, an exponential moving average of "were the first three drafted tokens all accepted" (the third position: prose 0.39–0.48, code 0.56–0.65, structured 0.89). With hysteresis it switches k in about six steps. A dynamic-speculation table keeps full CUDA graphs captured for both verify sizes.

What the variants say

  • All five capture the structured and sustained gains (+13–19% and +10–14%) and keep prefill unchanged. Code moves within noise (+2–4% for the optimistic starts).
  • Prose pays 4–6% in chat in every variant. The residual is structural: the drafter now evaluates six positions per step, and a request's first steps run at k=5 before the average settles. That gap is below what a reader notices at 40 tokens per second.
  • Long-context prose is where thresholds matter. Starting at k=3 (v2, v4) keeps it within 10% of production; starting at k=5 loses 15–18% on one of the two sizes. For this cluster's usage mix that cost was accepted in exchange for the concurrency of the optimistic start.
  • Per request beats per step for mixed parallel work: in per-step mode the slowest stream governs all four.
  • A closed side question. The bimodal four-stream waves were suspected to be mixed-k batches falling back to piecewise CUDA graphs. Fixed k=5 shows the same 177/224/224 pattern, so it is a property of k ≥ 5 at four streams, not of the policy.

Method, in short

Idle-endpoint gate before every pass (the engine's in-flight request counter must be zero, and the scheduler log is checked afterwards), correctness gate within two minutes of every boot, GPU temperature and clock snapshots around each pass (70–75 °C, 2405–2500 MHz, no throttle flag), acceptance read from the engine's own counters per phase. Two fresh-context code reviews against the image sources before the first boot; the first attempt disabled itself because it had subclassed the synchronous scheduler while this build runs the asynchronous one for DFlash2, and was rebased.

Next

  • The prose residual. −4..−6% by hand in every arm, so it is not a threshold effect: the drafter now evaluates six query positions per step instead of four, and a request's first steps run at k=5 before the average settles. The signal itself is marginal on prose — position 3 is accepted 0.39–0.48 of the time, which is where the band sits, so a prose request oscillates rather than settling. Next measurement: K_HI=3 on the same stack, drafter at 5 and verify at 3 everywhere, to separate the drafter and table cost from the policy cost.
  • Four-stream wave bimodality at k ≥ 5. Waves alternate between roughly 175 and 220–233 tok/s with fixed k=5 as well as with every adaptive arm, and v5 — where the batch is never mixed — shows it too, so piecewise CUDA graphs are not the cause. The slow wave is usually the first of a phase, which points at a warm-up of the four-stream shape. Until one slow and one fast wave are profiled side by side, no c4 median at k ≥ 5 should be read as a policy effect.
  • A K_HI=4 tier. The verify batch is k+1 tokens, so k=3 lands on the tuned M=4 entry of the GB10 MoE config while k=5 falls into the M=8 bucket. A k ∈ {3, 4} policy, or a tuner run that adds M=6, is the cheapest way to test whether part of the prose cost is a kernel-tile artefact rather than acceptance.

After that, the second phase-3 target found by profiling: about 29% of a decode step is spent in generic BF16 matrix kernels serving the layers the FP8 checkpoint leaves unquantized, a candidate for an INT8 or FP8 small-batch path.
