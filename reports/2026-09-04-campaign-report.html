Kept changes 1–3, and the four that were closed

Kept change 4, the adaptive draft length, has its own section below; the fifth kept item — all four hosts on one pinned kernel — is hygiene and sits in the night ledger.

kept

1 · --moe-backend triton instead of DeepGEMM

One engine flag. On sm121 the Triton fused-MoE path beats the patched DeepGEMM: decode +7..+16% across prompts, prefill +5%, no correctness change. The single biggest win of the campaign.

kept

2 · iommu.passthrough=1 on the four hosts

The SMMU was translating every DMA of the RDMA NICs and the GPU. A grub drop-in, one rolling reboot: structured +9%, c4 +8%, code +4..+7%, prefill and prose flat. Zero cost, versioned as a host script with --apply / --revert / --status.

kept

3 · the hybrid GB10 MoE config

vLLM's own kernel tuner (no Ray, plus a shim for this model) ran overnight on one node: 1152 tile configurations per batch size. The fully tuned file was +5–11% single-stream but −7% at 4 streams, because the tuner routes tokens uniformly and mis-tunes the 16–48 token sizes. The hybrid file keeps the tuned entries for 1–8 tokens only, and is worth single stream +6..+10% against the vLLM default. Bind-mounted into the container from the repo, with a launcher preflight.

closed

GPU clock lock

GB10 accepts nvidia-smi -lgc and ignores it: the SM clock sits at about 2540 MHz under load whatever you ask for. No gain available.

closed

GPUDirect RDMA

Structurally unavailable on this stack: CUDA reports no dma-buf and no GPUDirect RDMA support on GB10, the stock kernel has no peer-memory API, rdma-core 50 lacks the dma-buf registration call. Host bounce buffers stay. Measured on the ring anyway: NCCL is 4–5 ms of a ~65 ms decode step, so it is not the bottleneck.

failed

DeepGEMM without E8M0 scales

Boots, then generates garbage at temperature 0. Caught late once, which is why every experimental boot now passes a correctness gate within two minutes of coming up.

no-go

Rebuilding the vLLM image

Nothing usable upstream after the pinned commit: the sm120 CUTLASS FP8 grouped GEMM and the native sparse-MLA path are still open issues, the CuteDSL MoE is NVFP4-only. Tracked, not built.

Speculative tokens k = 3 / 4 / 5 / 7, with acceptance per workload

k=5: structured +16%, code +7%, sustained +11%, four streams +53% (224 tok/s), prefill flat, prose −10..−19%. k=7: structured +49%, sustained +38%, four streams +35%, code +8%, prose −12..−15%. k=4: prose already −14% with only +7% on structured. no gain

Prefill chunk 8192 → 16384 tokens

Prefill +0.5..+3% (inside the band), decode −4..−6% at the low edge of it. The 8192-token chunk already fills the GPU.

NCCL low-latency protocol (NCCL_PROTO=LL)

Kept change 4 — adaptive draft length (adaptive-k): k chosen per request

The k sweep left one decision open: k=5 buys structured output, sustained decode and four-stream throughput, and charges prose 10–19%. A 400-line scheduler subclass removes the choice.

Where it decidesIn vLLM's scheduler, not in the drafter. The drafter always drafts 5 tokens; the scheduler sets, per request, how many of them the next step verifies. One process decides and broadcasts, so the four tensor-parallel ranks stay consistent by construction.
The signalPer request, an exponential moving average (alpha 0.15) of "were the first three drafted tokens all accepted". Position 3 separates the workloads cleanly — prose 0.39–0.48, code 0.56–0.65, structured 0.89 — and hysteresis at 0.42 / 0.58 switches k in about six steps.
How it installsA subclass of vLLM's AsyncScheduler selected with --scheduler-cls and bind-mounted from the repo: no image file is replaced. SPEC_TOKENS=5 plus the dynamic-speculation table [[1,1,5],[2,6,3]] keeps full CUDA graphs captured for both verify sizes.

Decision — v1 promoted, 4 September 12:05.

Per-request k ∈ {3, 5}, optimistic seed 1.0, band 0.42 / 0.58, alpha 0.15, position-3 signal, SPEC_TOKENS=5 with the dynamic-SD table [[1,1,5],[2,6,3]]. The bench note recommended the safer v2; the owner chose v1 on the arm figures above:

  • The usage mix decides. About 50% parallel sub-agents driven by a third main model, 30% agentic coding with this stack as the primary model, 20% prose — so four-stream throughput and code decode carry the weight, and they are exactly what the optimistic seed buys: 201 aggregate (225 on the fast waves) against 144 at k=3 and 170–177 in the seed-3 arms, code 50.5 against 48.4, structured 68.6 against 57.6, sustained 58.9 against 53.4.
  • The prose cost is imperceptible. −6% single stream by hand, 40.2 against 42.9 tok/s: about 41 instead of about 43 tok/s is not something a reader sees. The same −4..−6% is present in all ten passes of all five arms, so protecting prose buys back no residual and costs the whole concurrency gain.
  • Batch-uniform rejected. v4 and v5 give the entire batch one draft length, so with concurrent heterogeneous requests the slowest stream governs k for everyone. Per-request mode lets each request keep its own — which is what a mixed sub-agent load is.
  • Costs accepted and recorded: prose −6% single stream, long-context essay decode −15..−20% on one size (100k 35.1 and 200k 36.2 against 43.8 / 42.5 at k=3), full decode CUDA graphs lost on mixed-k steps. Prefill unchanged.

Read against a public 3-node recipe

A public three-Spark recipe (jspark3) reports code 66 and structured 82 tok/s. It serves a different product: EXL3 experts at 4 bits, a BF16 trunk turned INT8 at load, three shards, DFlash2 at k=7, prose at 29 tok/s. Its own A/B credits the INT8 trunk overlay with +4..+7%; the rest is the 4-bit checkpoint, which our 1 September EXL3 window beat on every axis on four nodes before FP8 was chosen for quality. What transferred: acceptance-per-workload instrumentation (now in the harness), the replicated-drafter test (neutral here), the low-latency NCCL protocol test (closed), and, after the profile, the one idea that matters: the INT8 conversion of the linears our FP8 checkpoint leaves in BF16, which the profile charges with 29% of a decode step. What did not: expert parallel needs a complete graph, k=7 loses prose, and the engine already captures full decode graphs.

What we learned

  • Tune the kernel, not the fabric. The all-reduce ring is fast enough; the MoE kernel was the lever, pulled twice.
  • A kernel tuner that measures with uniform random routing lies about mid-size batches. Tune what the engine actually sees, or A/B in the engine.
  • Benchmarks need an idle endpoint. One confirmation pass was thrown away because a coding agent was talking to the cluster at the same time; the harness now checks the scheduler's in-flight count before and after.
  • Gate correctness before speed. A fast wrong answer looks like a slow right one in a throughput table.
  • Every change is an env overlay or a versioned host script with a one-step rollback. Nothing was tuned by hand on a node.

  5. Kept 3: the hybrid GB10 MoE config, kept only for 1–8 token batches (single stream +6..+10% vs the default). The fully tuned file lost 7% at 4 streams: vLLM's tuner routes tokens uniformly and mis-tunes the mid batch sizes. Tune what the engine actually sees.
  6. Kept 4: adaptive draft length. A 400-line scheduler subclass gives each request its own speculation depth (k=5 or k=3) from its own acceptance history. vs fixed k=3: structured +21%, c4 +56%, @1400 +17%, code +6%, prose −6% harness / 0% by hand.
  7. Kept 5, the boring one: the host tier. All four nodes on one pinned kernel, the passthrough drop-in and the MoE config shipped as versioned files, autostart from the head node, a from-zero runbook. Nothing on this cluster is tuned by hand on a node.
  8. Start → today: code 35.5→51.1 tok/s (+44%), structured 50.2→71.0 (+41%), 4 streams 127→228 (+80%), sustained 1400-token 45→63 (+40%), prose 34.3→42.7 (+24%), prefill 100k 2085→2209 (+6%). Two passes on the production recipe after a reboot, needle and tool-call PASS.
  9. Closed with evidence: fixed k=5 and k=7 (prose −10–19%), GPU clock lock (GB10 ignores it), GPUDirect RDMA (no dma-buf, no peermem), DeepGEMM without E8M0 (garbage at T=0), NCCL_PROTO=LL, a 16k prefill chunk, Marlin, a replicated drafter. Flat, worse, or broken.
  10. Caveats: ±5% boot-to-boot on decode, so small deltas are not results; prefill is bounded by the FP8 MoE kernel, not the fabric; adaptive k costs 3–14% of long-context essay decode. Repo, bench notes and raw JSON: the github.com/jnardiello/tp4-glm53-fp8-gx10 repository

Repository

Everything kept is code plus README: the recipe in cluster.env (Triton backend, config mount), the host tier under node/host/ and node/etc/ (passthrough drop-in and script), the tuned JSON under node/moe-configs/, the tuner under node/moe-tune/, the NCCL microbench under node/nccl-bench/, and one bench note per window under bench-results/ with the raw JSON of every pass.

What's next

Phase 3 opens where the profile points, not where intuition does. Nsight charges a decode step at 45% Triton MoE, 29% generic BF16 GEMMs, 9% NCCL — so three items, in that order:

  • An INT8 or FP8 small-M path for the BF16 remainder. The 29% is the linears the FP8 checkpoint leaves unquantized — the KDA o_proj, kv_b and lm_head — run by Ampere-era cutlass wmma kernels at tiny M, about 280 launches per step. Converting them at load time behind a quality gate on the output head is the largest single target left, and it is the one idea from the public 3-node recipe that transfers.
  • A fused KDA f/g projection. The linear-attention gates are two small launches per layer; fusing them attacks launch overhead in the part of the step the MoE does not own.
  • A decode-floor scheduler. A prefill chunk landing mid-conversation starves decode; a floor on decode slots per step is the scheduler-side answer, and the adaptive-k patch has now shown the scheduler is a safe place to change — subclass, bind mount, one rollback line.

Alongside them, the reproducibility package: the whole cluster rebuildable from nodes that only have OS, driver and docker — a node bootstrap script with --check / --apply, the patched NCCL vendored with its build and its checksum, a read-only node verifier, and an ordered from-zero runbook — plus the sanitized public mirror. The point is that none of the numbers on this page depend on a machine that was tuned by hand.

Still open behind those: a tuner run with realistic routing for the mid batch sizes (M=6 and M=24 matter now that k=5 is in the mix), the prose residual of the adaptive policy, and the prefill fabric share — NCCL is 27% of a prefill chunk, the next ceiling on that side.

Same harness for every number: medians of 3–5 runs, 200-token decode at temperature 0 with thinking off, prefill measured as prompt tokens over time to first token with a needle check. Production confirmation on 4 September: two passes, both verified clean against the engine's scheduler log. Decision rule: repeatable gain above the noise band with no regression, owner decides.
